### SECURITY

---

**[HIGH] S1 — Security**  
**File:** `supabase/functions/notify-on-message/index.ts:45–52`  
**Issue:** WEBHOOK_SECRET auth guard is conditional: `if (webhookSecret) { verify }`. If the `WEBHOOK_SECRET` env var is absent or unset after a redeploy, the check is skipped entirely — no authentication is performed and any HTTP client with the function URL can trigger push notifications to arbitrary users.  
**Risk:** An attacker who discovers the edge function URL (it is deterministic: `https://<project-ref>.supabase.co/functions/v1/notify-on-message`) can craft a POST that pushes spam notifications to every subscriber. The service role key is not exposed, so this is notification abuse rather than a data breach, but it erodes trust and may exhaust Web Push quotas.  
**Fix direction:** Make the guard fail-closed. If `WEBHOOK_SECRET` is absent, return `401` immediately. Add a startup assertion: `if (!webhookSecret) { console.error('WEBHOOK_SECRET missing — refusing to start'); Deno.exit(1); }`. Document the var as required (not optional) in `TRACK4_PUSH_RUNBOOK.md`.

---

**[MEDIUM] S2 — Security**  
**File:** `src/CoachApp.svelte:33–37`  
**Issue:** The `onAuthChange` handler unconditionally sets `view = 'dashboard'` for any `signed_in` or `recovery` status. `isCoachAllowed()` is defined at line 14 (checks `COACH_EMAILS`) but is never called in the auth callback. The `'denied'` view state is declared and rendered in the template but never set by the auth flow.  
**Risk:** Any user with a valid Supabase account who navigates to `/coach.html` and signs in gets a blank CoachDashboard. RLS blocks all coach-scoped writes, so no real harm is done, but the user has no feedback — they see an empty shell with no explanation.  
**Fix direction:** In the `signed_in` branch, check `isCoachAllowed(state.user)`. If false, set `view = 'denied'`. This is a 3-line change.

---

**[LOW] S3 — Security**  
**File:** `src/data/config.ts` vs `supabase_rls.sql` (`profiles.is_coach`)  
**Issue:** Two separate sources of truth for coach identity: `COACH_EMAILS` array in client config and `profiles.is_coach` DB flag. Must be kept in sync manually. No runtime check enforces consistency.  
**Risk:** If `is_coach=true` in DB but email not in `COACH_EMAILS`, the coach app blocks the user client-side (even though RLS would permit writes). Opposite case (in list, not in DB): app opens but all coach write RPCs fail with an RLS rejection and return silent errors (see Q2). More likely: confusion during onboarding of a new coach.  
**Fix direction:** Derive coach status from a single source. Simplest: remove `COACH_EMAILS` and make `CoachApp.svelte` read `profiles.is_coach` via a Supabase query on boot (`select is_coach from profiles where id = auth.uid()`). Removes the two-list maintenance burden.

### DATA INTEGRITY

---

**[HIGH] D1 — Data Integrity**  
**File:** `src/services/storage.ts:105–130`, `src/lib/state-merge.ts`  
**Issue:** `saveCloud` executes an unconditional Supabase upsert with no optimistic concurrency control (OCC). There is no `updated_at` check before writing; whoever upserts last wins.  
**Risk:** A user who trains on a phone (session A) then opens the same account on a tablet (session B, which loaded older cloud state on boot) and does additional work — the tablet's save will silently overwrite the phone's completed workout. Data loss is invisible to the user and there is no conflict warning. This is a real failure mode for any multi-device user.  
**Fix direction:** Add OCC at the upsert level: store `last_cloud_updated_at` locally at bootstrap time, then include `.eq('updated_at', lastCloudTimestamp)` in the upsert condition. If the condition fails (count = 0), the row was updated by another device — reload cloud state, re-run `chooseNewer`, and prompt the user: "A newer version was found on another device — which do you want to keep?" Alternatively, a lighter-weight option: at app-focus (`visibilitychange` to visible), re-fetch the cloud `updated_at` header only and warn if it is newer than the local blob.

---

**[MEDIUM] D2 — Data Integrity**  
**File:** `supabase_rls.sql` — `refresh_activity_summary()` trigger  
**Issue:** The trigger uses `(e->>'completed') = 'true'` to determine `last_trained_at` and `this_week_active`. The trainee app uses `dayHasActivity()` (any `set.done = true`, regardless of the `completed` flag). A trainee who performs sets but does not press "Finish Training" earns streak credit in the app but shows as inactive to the coach.  
**Risk:** Coach makes programme decisions based on activity data that silently diverges from the trainee's experience. "No activity this week" in the coach dashboard while the trainee's streak shows 3 done days. Undermines trainer-mode trust.  
**Fix direction:** Rewrite the `JSONB` aggregation in `refresh_activity_summary` to detect done sets instead of (or in addition to) the `completed` flag:  
```sql
max((e->>'date')::date) filter (
  where exists (
    select 1 from jsonb_array_elements(e->'sets') s
    where (s->>'done')::boolean = true
  )
)
```
Mirror this for the `this_week_active` field. After the change, re-run the RLS matrix.

---

**[MEDIUM] D3 — Data Integrity**  
**File:** `supabase_rls.sql` — `app_state_history` table + `prune_app_state_history` trigger  
**Issue:** 30 versioned snapshots are maintained per user in `app_state_history` but there is no client-side UI to browse or restore them. The table is append-only from the user's perspective — they cannot use it.  
**Risk:** If a user's blob is corrupted (e.g., by a schema migration bug, a rogue `updateState` call, or a `chooseNewer` edge case), their only recovery path is a developer manually running `SELECT state_json FROM app_state_history WHERE user_id = '...' ORDER BY snapshot_at DESC LIMIT 30` and doing a manual restore. At 1-user scale this is manageable; at any wider scale it becomes a support burden.  
**Fix direction:** Add a "Restore from snapshot" option to AccountSheet — show the 5 most recent snapshots with timestamps and a 1-line summary (e.g., "Week 69, 3 workouts"), allow the user to restore any of them. This is the highest-value safety net improvement.

---

**[LOW] D4 — Data Integrity**  
**File:** `src/components/AccountSheet.svelte:80–92`  
**Issue:** The "Clear data" flow calls `updateState(() => emptyAppState())` then `await saveCloud(user.id, emptyAppState())`. Both cloud writes are blocked by `hasData()` guard in `saveCloud` (returns false for a state with no exercises). The cloud is never cleared. Local state becomes empty; the cloud retains the full blob.  
**Risk:** A user who taps "Clear data" and then installs the app on a new device (or logs in elsewhere) gets all their data back. This may be a surprise. Positively framed: it's an accidental recovery net. Negatively: if the intent was to wipe data for privacy, it is not achieved.  
**Fix direction:** Either (a) document and toast: "Training history cleared on this device. Cloud backup retained — reinstalling will restore it." making the behaviour explicit, or (b) add a `force: boolean` param to `saveCloud` that bypasses the `hasData` guard when deliberately clearing. Option (a) is lower risk.

---

**[LOW] D5 — Data Integrity**  
**File:** `src/services/storage.ts` → `sanitizeState()`  
**Issue:** `sanitizeState()` normalizes exercise names via `normalizeExerciseName` only. It does not validate: negative or zero reps/kg values, exercises with an empty `code` string (type = 'superset' with no code breaks superset grouping), `WorkoutDay.date` values that are not valid ISO date strings, or sets arrays with zero elements.  
**Risk:** Malformed state can reach localStorage and cloud. For example, an exercise with `type: 'superset'` and `code: ''` groups with other empty-code exercises via `code[0]` — they all collapse into one unnamed block in `buildWorkoutBlocks`. Likely rare in practice but no guardrail exists.  
**Fix direction:** Extend `sanitizeState()` to filter out pathological values: clamp reps/kg to `>= 0`, filter exercises with empty names, add a `date` regex check on `WorkoutDay.date`.

---

**[LOW] D6 — Data Integrity**  
**File:** `src/services/sync.ts`  
**Issue:** When `saveLocal` throws `QuotaExceededError`, the error is caught, logged to console, and a toast is shown ("Storage full — local save failed"). The cloud save proceeds, but the local copy is out of date for the rest of the session.  
**Risk:** If the device goes offline after the quota error, new work is written to cloud but cannot be saved locally. An offline session started after this point sees stale local data and may overwrite the newer cloud state on next save via `chooseNewer` (local timestamp is newer than the pre-error cloud value for that session). Very low probability but no recovery heuristic exists.  
**Fix direction:** On `QuotaExceededError`, set a flag that suppresses the `chooseNewer` local-wins path for subsequent boots on the same device. Surface a stronger warning: "Local storage full — working from cloud only. Risk of data loss if offline."

### PERFORMANCE

---

**[LOW] P1 — Performance**  
**File:** `src/components/WorkoutMode.svelte`  
**Issue:** 32 Svelte 4 `$:` reactive statements in a Svelte 5 application. Svelte 5 supports this as legacy syntax but uses a less precise invalidation model than `$derived` — any store change in the component's reactive scope can retrigger all `$:` blocks, not only those whose dependencies actually changed.  
**Risk:** During a workout (the most latency-sensitive moment), rapid set toggles or timer ticks could trigger unnecessary re-computation. On mid-range mobile hardware, multiple `$:` recomputations in a single frame add jank to the most critical user interaction.  
**Fix direction:** Migrate the 32 statements to `$derived` and `$effect` runes. This is a refactor, not an urgent fix, but `WorkoutMode` is the highest-value migration target given it is the active-workout component.

---

**[LOW] P2 — Performance**  
**File:** `src/components/HeroCard.svelte`  
**Issue:** 13 Svelte 4 `$:` reactive statements — same pattern as P1. This is the primary above-the-fold component rendered on every app open.  
**Risk:** Lower than P1 (no workout-mode timing pressure) but contributes to initial render overhead.  
**Fix direction:** Migrate to `$derived` / `$effect` runes alongside P1. Both files together are the bulk of the legacy reactive surface.

### ARCHITECTURE

---

**[MEDIUM] A1 — Architecture**  
**File:** `src/components/AccountSheet.svelte:85–87`  
**Issue:** The "Clear data" flow calls both `updateState(() => empty)` (which enqueues a `scheduleSave` via the standard path) AND `saveCloud(user.id, empty)` directly (line 87). The direct call bypasses the canonical `updateState → scheduleSave` path. It is also redundant — it is blocked by `hasData()` (see D4).  
**Risk:** Creates architectural confusion: the code implies a direct `saveCloud` call is needed to clear cloud data, but it does nothing. A future developer might "fix" the no-op by removing the `hasData` guard without understanding why it exists, accidentally allowing an empty-state write to the cloud.  
**Fix direction:** Remove the direct `saveCloud` call on line 87. Add a comment explaining why cloud is not cleared (intentional safety net — see D4). If cloud clearing is desired, implement it explicitly as a separate RPC or a `force` param (see D4 fix direction).

---

**[LOW] A2 — Architecture**  
**File:** `src/services/state-parser.ts` — `KNOWN_SCHEMAS`, `parseAndMigrateState`  
**Issue:** No formal strategy for deploying a breaking AppState schema change. Currently `parseAndMigrateState` handles `4.0 → 4.1` and emits a console warning for unknown schemas, but continues. There is no documented process for what happens when schema `5.0` adds a required field (or renames `updatedAt`).  
**Risk:** A breaking change deployed to `gh-pages` runs against clients still on the old SW cache, which may hold schema `4.1` blobs in localStorage. If the migration path is not defined, `chooseNewer` could pick a local `4.1` blob and sync it back to the cloud, silently corrupting the cloud record for users who haven't refreshed.  
**Fix direction:** Document in `AGENT.md` / `OPERATOR.md`: "Schema bumps must be backwards-compatible migrations in `parseAndMigrateState`. A major version bump (e.g., field removal or type change) requires an interim deploy that reads both versions before a follow-up deploy that drops the old read path." No code change needed now — this is a process gap.

**[MEDIUM] X1 — Accessibility & UX**  
**File:** `src/components/MainView.svelte:58–62`  
**Issue:** Coach data loads (notes, assignments) are caught with:

try { await loadCoachNotesFor(me); } catch { /* notes optional */ }

## CLEAN RESULTS (areas with no issues found)

The following were audited and found clean — no finding raised:

- **Supply chain:** `npm audit` — 0 vulnerabilities. One production dependency (`@supabase/supabase-js@^2.106.2`).
- **RLS coverage:** All 10 tables have RLS enabled. All 7 authenticated-callable SECURITY DEFINER functions (`accept_coach_invite`, `revoke_coach_link`, `is_accepted_coach`, `has_accepted_coach`, `is_link_participant`, `mark_messages_read`, `caller_is_coach`) are within the expected advisory baseline.
- **Single-writer invariant:** Coach app does not call `scheduleSave`, `saveCloud`, or `saveLocal` on the trainee blob. RLS enforces this at the DB level. `CoachTraineeView.svelte` writes only to the in-memory Svelte store, not to Supabase.
- **Calendar performance:** `buildGrid()` renders only the current month (~28–35 cells). No virtualization needed.
- **Component cleanup:** All Svelte component event listeners and realtime subscriptions are properly cleaned up in `onDestroy`. `stopCoachUnreadWatch()` is called via `MainView.svelte`'s `onDestroy`, which fires on sign-out when the component unmounts.
- **VAPID public key:** Intentionally exposed in the client bundle — correct by design for Web Push.
- **App error tracking:** Stack traces are capped (500/2000 chars), URL is pathname-only. No PII beyond minified stack paths.
- **AccountSheet "clear data" cloud guard:** `hasData()` correctly prevents wiping the cloud with an empty state during the normal clear-data flow (see D4 for the intent vs. implementation gap).
- **Push bundle isolation:** `push.ts` is only imported via `AccountSheet → App.svelte` (trainee entry). The coach bundle does not include the push service.
- **Supabase free plan limits:** Well within bounds at current user count (DB < 5MB, realtime < 10 concurrent connections, edge function invocations < 1K/month).
- **iOS per-tab auth:** Per-tab storage adapter correctly isolates Supabase sessions. Cross-tab contamination fixed in `fac525c`. The re-login-on-memory-eviction trade-off is documented and correctly handled.
- **Bootstrap error path:** If both local and cloud fail at boot, `bootStatus = 'error'` and the boot overlay shows an error state. No silent failure.
- **Service worker update guard:** `if (get(uiState).workoutActive) return` correctly defers update checks during an active workout.
